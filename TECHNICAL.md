# ScheduleDisconnectLight — технічна документація

Секретів і ідентифікаторів чатів у файлі немає. Пов'язаний проєкт (дашборд і Worker): `C13PowerDashboard` (`TECHNICAL.md`, `INGEST.md`).

## 1. Що це і як влаштовано

Консольний застосунок (.NET Framework 4.7.2, C# 7.3), який запускається в GitHub Actions приблизно кожні 2 хвилини і за один запуск:

1. читає поточний стан інвертора Deye (мережа, генератор, батарея) і пише його в Google Sheet;
2. надсилає в Telegram повідомлення про появу/зникнення світла (з урахуванням графіка відключень);
3. формує графік відключень (ДТЕК, запасний варіант — Ясно), надсилає зміни графіка (з картинкою) і нагадування про заплановані відключення;
4. веде облік генератора: заправки, ТО, залишок палива, нагадування, винагорода за заправку;
5. передає знімок стану й дані журналу на Cloudflare Worker для сторінки `C13PowerDashboard`.

Стан між запусками зберігається у двох місцях: Google Sheet (світло/генератор, журнали, параметри) і файл `appState.json` у репозиторії (графік, прапорці відправлених повідомлень). Запуск не тримає нічого в пам'яті між запусками.

### 1.1. Порядок кроків `Program.Main`

| # | Крок | Помилка |
|---|---|---|
| 0 | `Parameters.Load()`: прочитати закладку `Parameters` | запуск завершується, нічого не робимо (наступний запуск спробує ще раз) |
| 1 | `PowerMonitor.Run()`: Deye → закладки `DeyeСтатус`/`DeyeСтатистика`, повертає подію зміни світла | лише в лог |
| 2 | `scheduleFormer()`: графік (ДТЕК/Ясно), порівняння з `appState.json`, повідомлення про зміну, нагадування, екстрені відключення | лог + повідомлення «Помилка в scheduleFormer» у тестову групу |
| 3 | `PowerMonitor.SendLightMessage()`: повідомлення про світло (після графіка, бо в тексті є розклад) | лише в лог |
| 4 | `GeneratorNotification.Form()`: показники, залишок палива/ТО, нагадування, повідомлення про заправку і ТО | лог + «Помилка в GeneratorNotification» у тестову групу |
| 5 | `WorkerSync.Run()`: передача на Worker (останнім, бо в знімку є текст показників з кроку 4) | лише в лог; `KV_LIMIT` → окреме повідомлення (розділ 9) |

Правило: збій одного кроку не повинен зупиняти наступні, тому кожен крок у власному `try/catch`. Помилки пишемо в лог (на GitHub він видно в Actions → крок «Run EXE»), у Telegram лише там, де це вирішено окремо.

## 2. Середовище запуску і режими

| | GitHub Actions («прод») | Локально (Visual Studio, «тест») |
|---|---|---|
| Визначення | `Api.IsGitHub()` | `!Api.IsGitHub()` → `Api.IsRegTest() == true` |
| Telegram | основна група | лише тестова група |
| Закладка `DeyeСтатус` | колонка C «Значення Прод» | колонка D «Значення ТЕСТ» |
| Журнали (`DeyeСтатистика`, `ЗаправкаСтатистика`, …) | звичайні рядки | рядок позначається «так» у колонці «Режим теста»; тестові й бойові рядки одне одного не бачать |
| Стан графіка | `appState.json` | `appState-local.json` |
| `WorkerSync` | працює | пропускається («тестовий режим, передачу на сайт пропущено») |
| Токен Deye | кеш Actions → `deye-token.json` | `deye-token.local.json` |

Свідомо передати дані на Worker з локального запуску: `"WORKER_SYNC_FORCE": true` в `appsettings.Local.json` (або змінна середовища `WORKER_SYNC_FORCE=1`).

`SendType` (`Service/Api.cs`) визначає куди йде конкретне повідомлення: `Auto` (за режимом запуску), `OnlyProd`, `OnlyTest` (завжди тестова група: технічні помилки, довідкові тексти), `ServiceGroup` (окрема службова група). Ідентифікатори груп/тем у `ConnectParam` (`Service/Api.cs`).

### 2.1. Workflow (`.github/workflows/main.yml`)

- Запуск: вручну (`workflow_dispatch`) і по `repository_dispatch` з типом `run-from-crone` (його надсилає зовнішній планувальник; вбудований `schedule` закоментований). `concurrency: state-updater1` без скасування: запуски стають у чергу, а не накладаються.
- Раннер `windows-latest`. Кроки: checkout → `git reset --hard origin/main` → створити `gcp-key.json` з секрету → відновити кеш токена Deye → запустити `ScheduleDisconnectLight\bin\Debug\ScheduleDisconnectLight.exe` → зберегти кеш токена (лише якщо токен оновився) → закомітити `appState.json`.
- **Запускається готовий exe з `bin\Debug`, який лежить у репозиторії.** Тому після змін коду треба зібрати проєкт у Visual Studio й закомітити `bin\Debug`. Без цього GitHub виконує стару збірку.
- Секрети GitHub: `BOT_TOKEN`, `ZVONOK_KEY`, `GCP_SA_KEY`, `CHAT_ID`, `DEYE_APP_ID`, `DEYE_APP_SECRET`, `DEYE_LOGIN`, `DEYE_PASSWORD`, `WORKER_URL`, `INGEST_SECRET`.
- `appState.json` комітить сам workflow (`git pull --rebase --autostash`, потім push). Через це в Visual Studio/GitHub Desktop регулярно виникають конфлікти по `appState.json`: вирішувати, залишаючи версію з GitHub, і перед комітом робити Pull.

## 5. Закладка `Parameters`

Усе, що можна вмикати/вимикати без нового релізу, керується з таблиці.

- `Parameters.Load()` читає закладку **один раз на початку запуску** (діапазон `A1:C200`). Не вдалося прочитати — запуск завершується. Значення за замовчуванням **немає**: якщо коду в таблиці нема, вмикач вважається вимкненим і в лог іде попередження.
- Вмикач `IsOn(code)`: `1`, `так` або `true` — увімкнено, усе інше (`0`, порожньо) — вимкнено.
- `GetString(code)` — рядок; `GetInt(code)` — ціле число (пробіли допускаються; не число → `null` і попередження в лог).
- Коди **не міняти** (їх використовує код); назви в колонці B вільні.

| Код | Значення | Де використовується |
|---|---|---|
| `GROUP_CODE` | рядок (код групи відключень) | `Api.CodeGroup`, графік |
| `TG_LIGHT_EVENT` | вмикач | повідомлення «світло з'явилось/зникло» (`PowerMonitor`) |
| `TG_OUTAGE_REMINDER` | вмикач | нагадування про заплановане відключення/відновлення (`Program`) |
| `TG_SCHEDULE_CHANGE` | вмикач | зміна графіка (з картинкою) |
| `TG_EMERGENCY` | вмикач | екстрені відключення введено/скасовано |
| `TG_FUEL_LOW` | вмикач | низький рівень палива, потрібна заправка |
| `TG_TO_NEEDED` | вмикач | потрібно планувати ТО |
| `TG_REFUEL_DONE` | вмикач | факт заправки генератора |
| `TG_TO_DONE` | вмикач | факт проведення ТО |
| `REFUEL_SALARY` | ціле число, грн | винагорода за одну заправку |

**Домовленість у коді:** перед кожною бойовою відправкою в Telegram стоїть явна умова `if (Parameters.IsOn(Parameters.X)) { … }` (не прихована всередині `SenderTelegram`). Перевірка діє і локально: `0` у таблиці блокує й тестову групу. Технічні повідомлення в тестову групу (`SendType.OnlyTest`) параметрами не керуються. Новий параметр: додати константу в `Service/Parameters.cs`, рядок у закладку, умову `if` у місці відправки.

## 6. Deye і стан будинку

### 6.1. `Service/DeyeClient.cs`

- Тільки поточний стан (`device/latest`), історію не читає. Квота Deye — 100 000 викликів на місяць, тому **один запуск = один виклик** плюс запит токена, коли старий спливає (з запасом 10 хв).
- Токен зберігається у файлі (`DEYE_TOKEN_FILE`). На GitHub цей файл відновлюється з кешу Actions між запусками. Коли застосунок отримав новий токен, він дописує `DEYE_TOKEN_REFRESHED=true` у `GITHUB_ENV`, і workflow зберігає кеш.
- Серійний номер інвертора заданий константою в `PowerMonitor` (щоб не робити зайвий запит).
- Час вимірювання Deye приходить як Unix-час або рядок; `ParseDeyeTime` приводить до київського.

### 6.2. `Service/PowerCalc.cs`

Порт правил із `C13PowerDashboard/lib/domain.mjs`: таблиця й дашборд мають рахувати однаково. **Змінюючи пороги тут, міняти й там.**

- Мережа/вихід: «є» — 180–260 В і 45–55 Гц на всіх очікуваних фазах; «немає» — менше 50 В і менше 1 Гц; між ними «нестабільна» (статус у таблиці при цьому **не змінюється**).
- Генератор (вхід GEN): працює при напрузі ≥ 150 В або потужності ≥ 800 Вт.
- Батарея: потужність по модулю < 70 Вт — «очікування»; при наявній мережі розряд < 150 Вт теж «очікування».
- Дані старші за 30 хв або без часу — застарілі, їм не вірити.

### 6.3. `PowerMonitor` і `DeyeSheet`

`PowerMonitor.Run()` порівнює новий стан зі станом у `DeyeСтатус`. Змінилися світло чи генератор → дописує рядок у `DeyeСтатистика` й **одним атомарним запитом** оновлює `DeyeСтатус` (дата статусу змінюється лише при зміні самого статусу). Реагуємо одразу, без підтвердження: хибні спрацювання відсікаються тим, що проміжні напруги ігноруються. Журнал: при зупинці генератора пишуться години роботи й пік потужності, коли з'явилося світло — скільки його не було.

Коди в колонці A `DeyeСтатус` (`DeyeCode`): `REQUEST_TIME`, `MEASURE_TIME`, `GRID_STATUS/DATE/VOLTAGE`, `GEN_STATUS/DATE/POWER/VOLTAGE/PEAK`, `INV_STATUS/DATE/LOAD`, `BAT_SOC/MODE/POWER`. Усі обов'язкові: якщо одного немає, програма скаже, якого саме. Нові рядки можна вставляти будь-де.

### 6.4. `LightMessage`

Текст повідомлення про світло: заголовок із часом події + цитата «скільки світла не було/було» + рядки про розклад. Варіанти: світло з'явилося (звичайне, раніше за розклад, без наступних відключень), зникло (за графіком, трохи раніше, позапланове), екстрені відключення, графік недоступний. Відключення «раніше розкладу» — якщо до початку за графіком не більше 30 хв (`EarlyWindow`). Про генератор у цьому повідомленні нічого немає.

## 7. Графік відключень

- `FormerScheduleFromDTEK` (+ `FormerScheduleFromDTEK_Parser`) розбирає дані з сайту ДТЕК; `FormerScheduleFromYasno` — запасне джерело. Порожній графік ДТЕК → повідомлення в тестову групу.
- `appState.json`: `SchedulesHash` (останній відомий графік), `IsEmergencyShutdowns`, `ScheduleDateLastUpdate`, `ScheduleHashDateSet`, `DateTimePowerOffLastMessage`/`DateTimePowerOnLastMessage` (за якими відключеннями вже надіслано нагадування) і `KvLimitAlertDate`. Зміна графіка порівнюється за хешем; при зміні шлемо повідомлення з картинкою (`ScheduleImageGenerator.Generate` повертає PNG) під параметром `TG_SCHEDULE_CHANGE`.
- Екстрені відключення (графіки не діють) → окремі повідомлення; нагадування за 30 хв до відключення/відновлення (`notifyBefore` у `Program.cs`, `TG_OUTAGE_REMINDER`); якщо в таблиці вказано, що світла і так немає, нагадування не надсилається.

## 8. Генератор: паливо, ТО, винагорода

- `GeneratorStatus` читає `ЗаправкаСтатистика`, `ТОСтатистика`, журнал `DeyeСтатистика` й рахує години роботи після останньої заправки/ТО, залишок палива (за середнім розходом `СередніВитрати`), місячну статистику користувача. Об'єм бака — 120 л (константа `ParamRefuel._totalLitersInGenerator`).
- `GeneratorNotification.Form()` формує текст показників (HTML Telegram), пише його в нотатку закладки `Показники` і запам'ятовує в `LastIndicatorsHtml`/`LastIndicatorsAt`; звідти його бере `WorkerSync`.
- Нагадування про паливо: залишок ≥ 3 год — все гаразд (стан скидається); від 0,5 до 3 год — повідомлення «потрібна заправка» щоразу, коли залишок впав ще на годину від того, про який уже сповіщали. Про ТО: залишок ≥ 75 мотогод — гаразд; від 1 до 75 — повідомлення при падінні на 25 год; менше 10 — «критичний рівень». Про що вже сповіщали, зберігається в таблиці (`getHoursRefuel/saveHoursRefuel`, аналогічно для ТО).
- **Повідомлення про заправку** (`TG_REFUEL_DONE`) шлеться для рядка, де «Відправлено в TG» ≠ «так». Винагорода: `REFUEL_SALARY` з `Parameters` (завжди з параметра, не з колонки M) записується в колонку M рядка заправки (ставка фіксується в історії). Місячна сума = сума колонки M інших заправок користувача за місяць + поточна. Немає параметра → рядки про винагороду не показуються і M не пишеться. Google Apps Script, що рахує звіт винагород, має брати суму з колонки M (`u.sum += Number(r[12]) || 0`).
- `ТО`: аналогічно (`TG_TO_DONE`).
- Кнопки під повідомленнями (`GetReplyMarkup`, `ReplyMarkup`): заправка, показники, винагорода, ТО тощо; ведуть у бот/веб-частину.

## 9. Передача даних на Worker (`Service/WorkerSync.cs`)

Контракт: `C13PowerDashboard/INGEST.md` (`schemaVersion` 1). Кожен запуск:

1. читає журнал (`DeyeСтатистика`) й заправки (`ЗаправкаСтатистика`, A:K), рахує їх хеші (SHA-256 від компактного JSON, 32 символи);
2. `POST /api/ingest`: знімок поточного стану (`gridStatus`, `genStatus`, `genPower`, `soc`, `batteryMode`, `batteryWatts`, `loadWatts`, `indicatorsHtml` тощо) і хеші;
3. Worker відповідає `needJournal`/`needRefuels` (його хеш інший) → лише тоді шлемо повні блоки (`/api/ingest/journal`, `/api/ingest/refuels`). Ручні правки таблиці теж потрапляють на Worker самі;
4. тестові рядки й рядки «Не враховувати» заправок не передаються.

`Post()` додає заголовок `X-Ingest-Secret`; не-2xx → виняток `Worker <код>: <відповідь>` (секрет у текст не потрапляє).

**`KV_LIMIT`.** На безкоштовному плані Cloudflare KV дозволяє 1000 записів на добу. Коли ліміт вичерпано, Worker відповідає `503 {"error":"KV_LIMIT"}`. `Program.NotifyKvLimit()` тоді шле яскраве повідомлення («САЙТ НЕ ОНОВЛЮЄТЬСЯ») у тестову групу не частіше разу на добу; дата останнього — `KvLimitAlertDate` в `appState.json`. Ліміт скидається о 00:00 UTC.

## 10. Telegram (`Service/SenderTelegram.cs`)

Властивості: `SendType`, `Photo` (PNG, відправляється як фото з підписом), `ReplyMarkupObj` (кнопки), `AddLinkDashBoard` (додає посилання на дашборд), `SendInChatIdThreadAddition` (додаткова тема для показників). Повідомлення в форматі HTML (`parse_mode`). Одне нове повідомлення — це один виклик `Send`; повтори робить код навколо (напр. `PowerMonitor` — до 3 спроб для повідомлення про світло).

## 11. Правила розробки

- **Нові `.cs` файли додавати в `ScheduleDisconnectLight.csproj`** (`<Compile Include=…>`, SDK-style немає). Інакше файл не збереться.
- C# 7.3 (немає `switch`-виразів, `??=` тощо). Проєкт не збирається поза Windows/Visual Studio.
- Файли мають змішані перенесення рядків (CRLF/LF) і BOM: правити, не міняючи їх масово (інакше величезні diff).
- Після змін: зібрати в Visual Studio → закомітити разом із `bin\Debug` (workflow запускає exe звідти) → `Pull` перед `Commit`, бо бот править `appState.json`.
- Консоль-тул для аналізу історії Deye (періоди роботи генератора за N днів у CSV/Excel): окремий проєкт `Deye\ConsoleApp60`, режим `--generator-history --days=N`. Нічого не пише в таблиці.

## 12. Типові проблеми

| Симптом | Причина / дія |
|---|---|
| «Не вдалося прочитати закладку Parameters, запуск пропущено» | Google Sheets тимчасово недоступний або закладка порожня; наступний запуск спробує ще раз. |
| Повідомлення не надходить, у лозі «параметра … немає в таблиці» | Немає рядка з кодом у `Parameters` або там не `1`; додати/виправити. |
| «Для Світло … не заполнена дата с/по» (тестова група) | `GeneratorStatus.getRangeGen`/`fillRanges` збирає з `DeyeСтатистика` періоди: для «Світло» `0` = зникло (початок), `1` = з'явилось (кінець); для «Генератор» `1` = запуск, `0` = зупинка. Рядки з «так» у «Режим теста» пропускаються. Повідомлення означає, що для вказаної дати немає пари (кінець без початку, або навпаки). Перевірити рядки журналу навколо цієї дати й порядок записів. Причину в конкретному випадку з'ясовувати по лозі (`Журнал …, рядок N`). |
| `Worker 401` у лозі | Не збігається `INGEST_SECRET` у GitHub і на Worker. |
| `Worker 503: KV_LIMIT` | Вичерпано 1000 записів KV на добу; сайт покаже старі дані до 00:00 UTC. |
| «WorkerSync: тестовий режим…» | Локальний запуск: передача пропускається, це нормально (`WORKER_SYNC_FORCE` для перевірки). |
| Конфлікт `appState.json` у Git | Бот пише цей файл кожні 2 хв: залишити версію з GitHub, у майбутньому робити Pull перед Commit. |
| GitHub виконує старий код | Не закомітили зібраний `bin\Debug`. |
| «Commit failed» у GitHub Desktop | Лишився `.git\index.lock`: закрити програми Git і видалити файл. |
| Квота Deye | Один виклик на запуск; не додавати зайвих викликів `device/*` і не запитувати токен без потреби. |
